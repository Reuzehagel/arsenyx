Arsenyx data pipeline — v3 (empirically grounded)

Rewrite of v2 after actually fetching DE PublicExport, the wiki Lua modules, and probing the wiki API. v2 was based on educated guesses about field shapes; several of those guesses were wrong. This version cites what we observed.

What changed since v2. Empirical fetches of ExportWeapons_en.json, ExportUpgrades_en.json, Module:Weapons/data/primary, and Special:Version showed: (1) DE has no parentName on weapons, no compatibilityTags, no polarities — the v2 "parentName walker" was fictitious; (2) DE does ship pre-computed mod levelStats — the "keep WFCD for levelStats math" justification is dead; (3) the wiki Lua modules already carry Class, CompatibilityTags, Polarities, ExilusPolarity, Family, Slot, Traits as clean separate fields — the v2 "displayClass + compatTags split" was reinventing what the wiki already does; (4) the wiki has no Cargo or Bucket query API populated (yet) — we fetch raw Lua and parse it.

The architecture in one sentence

Two upstream sources, each authoritative within its lane: DE PublicExport for game numbers, wiki Lua modules for player-facing classification and polarities. We own the merge, the schema, and a small curated overrides layer. @wfcd/items drops out entirely.

What we verified empirically

Confirmed against live endpoints (2026-05-27)

  • DE ExportWeapons_en.json — 831 weapons, top-level fields: name, uniqueName, codexSecret, damagePerShot[20], totalDamage, criticalChance, criticalMultiplier, procChance, fireRate, masteryReq, productCategory, omegaAttenuation + category-conditional (accuracy/trigger/reloadTime/multishot/magazineSize for guns; blockingAngle/comboDuration/slamAttack/... for melee). No parentName, no compatibilityTags, no polarities, no exilus.
  • DE productCategory has only 8 values across all 831 weapons: Pistols (327), Melee (221), LongGuns (192), SpecialItems (36), SentinelWeapons (24), SpaceGuns (22), SpaceMelee (8), OperatorAmps (1). Bubonico AND Hek AND every sniper rifle are all just LongGuns. DE makes no shotgun/rifle/sniper distinction.
  • DE ExportUpgrades_en.json (mods) ships fully-populated levelStats arrays — Serration's 11 ranks of "+15% Damage" … "+165% Damage" come straight from the export. No WFCD math required.
  • DE clean English names: present inline in _en.json. "name": "Coda Bubonico". PEP's dict.en.json split is a multi-locale dedup optimization we don't need (English only).
  • Wiki Module:Weapons/data/primary for "Coda Bubonico" carries: Class = "Arm-Cannon", CompatibilityTags = { "PROJECTILE", "AOE", "BATTERY" }, ExilusPolarity = "Madurai", Family = "Bubonico", Mastery = 17, Polarities = { "Naramon", "Madurai", "Naramon" }, Slot = "Primary", Traits = { "Infested" }. Surprises worth knowing

  • Arcanes live in ExportRelicArcane_en.json despite the filename. 168 cosmetic-enhancer entries with levelStats already populated — 67 named Arcane … proper, plus Exodia, Theorem, Magus, Virtuos, Pax. Filed under /Lotus/Upgrades/CosmeticEnhancers/ in the uniqueName tree — quirky DE choice.
  • One wiki file covers four categories. Module:Warframes/data contains Warframes, Archwings, Necramechs, and Operators as named subtables. One fetch, four item types.
  • DE's ExportSentinels undercounts pets — only 15 KubrowPets, vs the full menagerie on the wiki. Wiki is the authoritative source for companions.
  • Modular weapons (Zaws / Kitguns / Amps) have no per-build DE entry — they're composed at runtime from parts. DE exports the parts; wiki documents valid combos and base-class stats. The planner has to either expose parts-as-components or list common preset combos as curated entries. This is a UX choice, not a coverage gap.
  • Operators are wiki-only. No DE export. The wiki carries them in Module:Warframes/data → Operators. Fine for our purposes — operators don't have many mod-relevant fields anyway.
  • Beast claws have Class = "Claws (Beast)" in Module:Weapons/data/companion with full damage tables. Confirms scripts/beast-claws.ts's 322 LOC of hardcoded data is now deletable.

Mockup: the mod-compat rule (three fields, not one)

The earlier draft claimed a single compatTags.includes(mod.compatName) would do it. It won't — DE's compatName vocabulary (Pistol, Rifle, Parazon, Necramech, mixed case, slot/role) and wiki's CompatibilityTags (PROJECTILE, AOE, HITSCAN, BATTERY — uppercase capabilities) are different vocabularies. They compose, they don't substitute. So we carry three fields per weapon:

FieldSourcePurposeBubonico example
displayClassWiki ClassUser-facing label in the UI"Arm-Cannon"
modPoolDE productCategory + compatibilityTags on the weapon, with wiki override when DE disagreesSlot-level mod-pool routing (which compatName bucket the weapon draws from)"Shotgun"
compatTagsWiki CompatibilityTagsCapability refinements (Cautious Shot only on PROJECTILE+AOE, etc.)["PROJECTILE","AOE","BATTERY"]

Bubonico is the canonical divergence: shown as Arm-Cannon, drawn from the Shotgun mod pool, refined by PROJECTILE/AOE/BATTERY. None of the three fields collapses into another — and that's exactly why WFCD's wiki-merge step broke when it dropped wiki Class.

packages/shared/src/warframe/mods.ts — predicate was ~80 LOC of string guessing
// before: isPrimaryMod / isPistolMod / isMeleeCompat / modMatchesCompat (~80 LOC of name+category guessing) // after: two structural checks, both reading data we own. function weaponAcceptsMod(weapon, mod) { // 1. slot/class pool match — normalize DE's mixed-case compatName at build time if (weapon.modPool !== mod.compatName) return false; // 2. capability refinement — mod may demand specific weapon tags if (mod.requiredTags?.some(t => !weapon.compatTags.includes(t))) return false; if (mod.forbiddenTags?.some(t => weapon.compatTags.includes(t))) return false; return true; } // Outer routing (necramech, plexus, railjack, stance-by-meleeClass) still wraps this. // The bug surface that broke under WFCD is gone: modPool and compatTags are structural data, // not derived guessing — and displayClass is decoupled from both.

modPool source — one line plus a small override map

For the overwhelming majority of weapons, modPool = displayClass. Hek is class "Shotgun" and pulls from the Shotgun pool. Boltor is class "Rifle" and pulls from the Rifle pool. Etc. The interesting cases are the Arm-Cannon family, where display and pool diverge:

data/curated/mod-pools.yaml — the entire file scope verified 2026-05-27
# Override map: weapon name → mod pool, when displayClass alone is wrong. # Default rule (in build script): modPool = displayClass. # This file lists only the exceptions. Shedu: Rifle # Class="Arm-Cannon", rifle-pool Bubonico: Shotgun # Class="Arm-Cannon", shotgun-pool "Coda Bubonico": Shotgun Sepulcrum: Pistol # Class="Arm-Cannon" secondary variant # …expected total: under 20 entries

Verified empirically: neither DE nor Module:Weapons/data distinguishes Shedu (rifle-pool) from Bubonico (shotgun-pool) — both are Class = "Arm-Cannon", both AmmoType = "None", both same top-level field set. CompatibilityTags differ (Shedu has ASSAULT_AMMO, Bubonico doesn't) but ASSAULT_AMMO is not a rifle/shotgun discriminator — Hek (shotgun) also has it. So there's no structural source. A small curated YAML is the answer: a few entries, reviewed against the wiki Arm-Cannon page on every data bump, fail-loud on any weapon whose displayClass isn't a known mod pool and isn't in the override map.

Mirror, don't fetch-at-build

Both upstreams get checked into the repo as raw snapshots. The build reads from disk, never from the network.

data/raw/de/ // LZMA-decoded JSON snapshots (16 files) data/raw/wiki/ // raw .lua mirror, one file per module (15 files) data/curated/ // our overrides data/PINS.json // DE index hash (wiki pin is implicit — the files ARE the pin)

Consequences: git diff is the wiki changelog; the auto-update bot's PRs show real data deltas alongside any code that has to absorb them; rollback is git revert; builds are reproducible from a repo clone with no network. Cost: ~17 MB of mirrored text in the repo (compresses well).

The Lua-parsing piece (only non-obvious bit)

Wiki has no Cargo and Bucket is unused. The update step fetches raw Lua via ?action=raw and writes it to data/raw/wiki/. The build step reads those files and parses them with luaparse (pure-JS, well-maintained npm package). The subpages we actually consume are pure data — no functions, no require, no metatables — so we extract a single top-level table literal per file. ~50 LOC of glue.

Note on Module:Weapons/data: the parent module is a 157-line router that uses mw.loadData, metatables, and overridden pairs to lazily proxy to subpages. We do not parse the router — we only mirror and parse the 8 subpages it declares: { primary, secondary, melee, archwing, companion, railjack, modular, misc }. The router's existence is what guarantees the subpages stay pure-data (Scribunto's mw.loadData contract forbids functions/metatables in the loaded module), which is what makes them safe to luaparse.

LZMA in Bun: Bun has no built-in LZMA. DE's index_en.txt.lzma is raw LZMA1 (not .xz). Pin a pure-JS package — lzma on npm works in Bun, ~10 LOC of glue. lzma-native is a node-gyp binary, avoid.

Forward compatibility win. Gloop has installed the Bucket extension on wiki.warframe.com but hasn't populated any buckets yet. When they migrate Weapons/Mods to Bucket (probably in the next year — the extension's clearly there for that), we swap our fetch-wiki.ts from "raw Lua + parse" to "action=bucket JSON query," and the rest of the pipeline doesn't change. Free upgrade.

Risks and mitigations

Risk

Wiki name doesn't match DE name

DE: "Coda Bubonico". Wiki module key: "Coda Bubonico". Usually they match, but variants and rename events can diverge. Mitigation: alias table in data/curated/wiki-aliases.yaml; comparison harness reports unmatched DE entries.

Risk

Wiki lag after game patches

Wiki editors update within hours-to-days of a Warframe patch. Until they do, a new weapon has DE stats but no wiki Class. Mitigation: fail-loud on missing wiki record by default, with a --allow-partial dev flag that emits with class: null and a build-time warning.

Risk

Lua parse breakage on syntax drift

Wiki editors occasionally introduce Lua expressions luaparse doesn't handle (rare — modules are almost entirely table literals). Mitigation falls out of the mirror layout: the update-bot's PR fails CI, the bad .lua file never lands in data/raw/wiki/, and the build keeps using the last good snapshot until luaparse is fixed or a curated patch is added.

Mitigation built in

Future Bucket migration

If Gloop migrates wiki to Bucket queries, fetch-wiki.ts swaps from raw-Lua to action=bucket. Rest of pipeline unchanged. We pre-design fetch-wiki.ts as a pure "module name → JS object" function so the swap is one file.

Risk

Wiki content is CC-BY-SA

Mirroring .lua files into the repo means we redistribute CC-BY-SA-licensed text. The license is fine for our use (commercial, donations, ads — all permitted; warframe-items does the same thing under MIT code). Obligations: attribute the wiki and note the license on the mirrored content. Mitigation: data/raw/wiki/ATTRIBUTION.md with source URLs + CC-BY-SA notice. Our code/site stays under its existing license — SA only attaches to derivatives of the SA'd content, not the surrounding code.

Risk

DE productCategory enum drift

DE has historically added new values (MechSuits shipped with Necramechs). The 8 values today: Pistols, Melee, LongGuns, SpecialItems, SentinelWeapons, SpaceGuns, SpaceMelee, OperatorAmps. Build step asserts against a frozen KNOWN_PRODUCT_CATEGORIES set and fails loud on unknown — silent miscategorization becomes impossible. When DE adds one, build fails on the next data bump, we update the set + the productCategory → modPool mapping in the same commit.

Risk

Update bot blocks unrelated CI on new-weapon lag

If DE ships a new weapon before wiki editors document it, fail-loud on missing wiki record would block any data bump. Mitigation: data/curated/wiki-stubs.yaml escape hatch — keys a weapon by uniqueName with a minimal hand-filled record and a stubUntil date. Build warns on every stub; CI fails if any stub is past its date. Forces stub cleanup without blocking the bot.

What we explicitly aren't doing

  • Forking WFCD. Their value-add was the wiki-merge step; we go to the wiki directly and skip the buggy middleman entirely. Forking would inherit their bugs.
  • Adopting PEP. Bus factor 1, no polarities anyway, opaque Pluto+WASM derivation. v2's rejection stands.
  • Collapsing display/pool/refinement into one field. v2's displayClass/compatTags split was on the right track — we extend it to a three-field model (displayClass + modPool + compatTags) because wiki CompatibilityTags are capabilities (PROJECTILE/AOE), not slot/role names, and so they don't replace the pool routing. See the mod-compat mockup.
  • Hosting our own image CDN. DE's content.warframe.com/PublicExport/ already serves icons via ExportManifest.json's textureLocation. Use it.
  • Drop tables / acquisition. Out of scope for now. Wiki has Module:DropTables/data — accessible later via the same Lua-fetch pipeline if/when we want acquisition info in the planner.
  • i18n. Locked English-only. Wiki Lua modules are English-only anyway; multi-locale would require a different data strategy. Deferred.
  • Modular weapon composer (Zaws / Kitguns / Amps). Both DE and wiki ship the parts; neither ships per-build entries. Whether the planner exposes parts-as-components (let users assemble a Zaw from prism + scaffold + brace) or surfaces curated common combos is a UX call, not a data-pipeline call. Deferred to a separate spec.

The TL;DR

DE PublicExport (game numbers, levelStats, icons) + wiki Lua modules (Class, CompatibilityTags, Polarities, ExilusPolarity, Family, Slot, Traits) + small data/curated/*.yaml overrides — all three checked into data/raw/ and data/curated/ as a repo-local mirror. Three reads, one merge, our schema, our repo, our pins. Build never touches the network; git diff is the wiki changelog; rollback is git revert. Drop @wfcd/items entirely. ~460+ LOC deleted (beast claws confirmed wiki-covered). The Bubonico bug becomes structurally impossible because we read wiki Class directly, not WFCD's broken wiki-merge derivation.
