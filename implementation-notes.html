Branch + repo organization

Branched data-pipeline-rewrite off data-pipeline-rewrite-plan, not main

decision2026-05-27

The plan doc says implementation lives on data-pipeline-rewrite but doesn't specify the parent. Branching off the plan branch keeps both the spec docs and the implementation in the same working tree.

Curated data format: TypeScript modules, not YAML

TS instead of YAML for all curated overrides

deviation2026-05-27

The plan shows curated files as YAML (mod-pools.yaml, etc.). Bun has no built-in YAML and CLAUDE.md forbids adding deps without approval — the plan pre-approves luaparse and lzma but not a YAML parser. I switched to TypeScript modules: type-safe, supports comments, no parser, build script imports them naturally. Net effect: same fields, slightly different syntax (curly braces and colons instead of YAML indentation).

Files: data/curated/{mod-pools, class-pools, wiki-aliases, wiki-stubs, plexus, atmospheric-archgun}.ts. Say the word and I'll swap to YAML if you prefer.

DE PublicExport URL pattern

Plan's URL pattern is wrong; correct one found in WFCD source

deviation2026-05-27

The plan's sync-de.ts sample uses /PublicExport/Lzma/${hash}. That 404s for every blob. Actual pattern (from WFCD/warframe-items build/scraper.ts): 

https://content.warframe.com/PublicExport/Manifest/<name>!<hash>

Two corrections: (1) path is /Manifest/ not /Lzma/; (2) the full name!hash is the path segment, not just the hash. Plus: blobs at /Manifest/ are plain JSON, not LZMA — only the index is compressed.

lzma dep is still needed for the index. bun run scripts/sync-de.ts now produces all 16 blobs (~19 MB uncompressed).

lzma sync API is callback-based, not synchronous

decision2026-05-27

Plan shows import { decode as lzmaDecode } from "lzma" with synchronous use. Actual package exports decompress(bytes, onFinish, onProgress) with onFinish(result, error) (unusual arg order). Wrapped in scripts/build/lzma.ts as promises.

NUL byte regex

Spec text contained an invisible NUL; explicit \x00 instead

deviation2026-05-27

raw.replace(/\x00/g, "") instead of a literal NUL byte in the regex source. Plain ASCII, reviewable in any editor.

Lua parser quirks (Phase 2)

encodingMode: "none" + manual unescaper

deviation2026-05-27

Wiki content has U+2019 (smart quote in Mag's), U+014D (ō), U+00E9 (é) which luaparse's pseudo-latin1 and x-user-defined modes reject. Stayed in "none" and wrote a Lua-string unescaper that reads .raw and processes \n \t \\ \xNN \u{H..H} \ddd \z. Handles double-quoted, single-quoted, and long-bracket forms.

Three "return" shapes per module

decision2026-05-27
  • return { ... } — most modules. Direct.
  • local Foo = { ... }; return Foo — Avionics, Mods. I track top-level local declarations and resolve the return.
  • return wrap(Data) — Stances uses addSharedCombos(StanceData). I unwrap to the function's first argument. Followup: if we ever surface stance combo data, this bypass becomes a bug — we'd miss the shared Heavy/Slide/Aerial/Wall/ Finisher/Slam combos.

Soft-handling capitalized booleans + unquoted strings

deviation2026-05-27

Wiki editors occasionally type IsSilent = False (capitalized) or Procs = { "", Knockdown, "" } (unquoted string in a string array). Soft-handled: True/False/Nil become the literals; any other bare identifier becomes a string of its own name, with a one-time console.warn.

Plan says "fail loud on drift" but these aren't drift in the load-bearing sense — they're typos in unambiguous positions. The audit trail is in the warnings. KNOWN_* assertions in merge-weapons.ts still fail loud on semantic drift.

math.huge allow-list

decision2026-05-27

Wiki uses math.huge for instant-fire weapons. Small allow-list: math.{huge,pi,maxinteger,mininteger}. Anything else fails loud. Followup: JSON.stringify(Infinity) emits null, so the merge step will need to either convert these to a finite sentinel or emit them as a string. open (see Open questions).

BinaryExpression: constant-fold arithmetic

decision2026-05-27

Wiki uses inline arithmetic for derived stats — e.g. HeavyAttack = 510 * 2. I evaluate + - * / % ^ .. at parse time; everything else fails loud. Output schema gets the computed value (1020), not the expression.

modPool is a list, not a string (Phase 4)

Plan's "modPool = displayClass" rule doesn't survive contact with the data

deviation2026-05-27

Empirical findings after enumerating DE compatNames + wiki Class values:

  • 232 distinct compatName values in DE — mostly coarse pools (Rifle/Shotgun/…) but also per-weapon augment names (Hek, Vulkar), per-frame augment names (Excalibur, Volt), and stance compat names (Polearms, Hammers — PLURAL for stances vs singular for weapons).
  • 62 distinct wiki Class values — 30+ are melee subclasses (Polearm, Hammer, Heavy Blade, …) that all map to the single "Melee" mod pool plus a stance-specific compat pool.
  • Multi-pool weapons are common — a sniper rifle accepts "Rifle" AND "Sniper" mods; a Polearm accepts "Melee" AND "Polearms" stance mods; an Excalibur accepts "WARFRAME" AND "Excalibur" augments.

So modPool is a list, not a string. The schema field is modPools: readonly string[]. The merge computes it by:

  1. Class-default lookup (data/curated/class-pools.ts) → coarse pool list per wiki Class.
  2. Per-name override (data/curated/mod-pools.ts) replaces the class default when needed (Arm-Cannon family).
  3. Plus the weapon's own name (for augment matching).
  4. Plus the base name if it's a Coda/Kuva/Tenet variant.

The plan's "under 20 entries" claim holds for the per-name override table (mod-pools.ts) — I shipped 4 entries (Shedu/Bubonico/Coda Bubonico/Sepulcrum). But the class default table needs ~60 entries to map every Class to its pool list. Both are tabular, no logic — drift surfaces in the KNOWN_MOD_POOLS assertion.

Mod-compatibility predicate stays simple, just one extra layer of "includes": 

function weaponAcceptsMod(weapon, mod) {
  return weapon.modPools.includes(normalizedCompatName(mod))
}

If you'd prefer to keep modPool singular and handle the multi-pool case differently (e.g. mods with multiple compatNames), say so. The current shape feels right because DE's source-of-truth compatName is the singular value — it's the weapon's pool membership that's plural.

Polarities: full names, not abbreviations

Merge stores "madurai" / "vazarin" etc. — UI codec abbreviates

decision2026-05-27

The existing arsenyx normalizePolarity() in shared/warframe/mods.ts already maps abbreviations ("v", "d", "r", "dash") → full names. The spec mockup showed abbreviated polarities in the merge output, but storing the canonical full name keeps the merge output unambiguous and lets the existing UI mapping handle presentation. Net: polarities: ["naramon", "madurai", "naramon"] instead of ["V", "D", "V"].

Resolved questions (you steered)

Curated format: TypeScript (UX call confirmed)

resolved

You asked for "whatever is best UX". After honest comparison, I'm sticking with TS: in a TS codebase, having scattered YAML for ~4-line override tables feels inconsistent, and typo-catching at typecheck time (not build-runtime) is real value. The override files have detailed JSDoc that surface as hover-doc in your editor; the type system catches typos like "Shotugn" vs "Shotgun". If you'd rather have YAML, swap is mechanical — say the word.

modPools as list (confirmed)

resolved

Implemented as readonly string[]. Validated with the real DE mod data: Lanka (Sniper Rifle) accepts 90 mods (Rifle + Sniper + Lanka), Pyrana Prime (Shotgun Sidearm) accepts 186 (Pistol + Shotgun + Pyrana Prime), Orthos Prime (Polearm) accepts 108 (Melee + Polearms + Orthos Prime). The singular-string model could only have routed one of these correctly.

math.huge serialization: null + opt-in flag

resolved

Approach: field is null in JSON (clean round-trip via JSON.stringify(Infinity) → null), plus an isInstantFire?: true companion flag for the few weapons/arcanes where the distinction matters.

Empirical update: after running the weapon merge, zero numeric fields actually surface as null because the merge prefers DE numeric stats (real numbers) over wiki (where math.huge lives). So the flag plumbing only needs to land if Phase 4's arcane/mod merges encounter it. Deferring until then.

Polarities: lowercase full names (confirmed)

resolved

Merged output stores "madurai" / "vazarin" / "naramon" in full. Phase 5 will need to verify URL codec compatibility — the existing shared normalizePolarity() already accepts both abbreviations and full names, so this should be smooth.
